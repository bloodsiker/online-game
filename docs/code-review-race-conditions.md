### Этап 1В — казна, продажа и стаки покупок: завершён (2026-11-02)

Закрыт критический пункт **6** (`SellItems`), гонка снятия из казны и замечание к стакам в обычном/премиум-магазине.

- Внесение и снятие денег из казны используют единый порядок блокировок `clan → user → membership → role`. После блокировки заново проверяются членство, актуальные права, оплаченный налог и балансы. Списание защищено SQL-условием достаточного остатка; проверяются предельные суммы до изменения денег.
- Изменение обоих балансов, запись в журнал казны и общий клановый журнал выполняются одной транзакцией. При ошибке лога деньги откатываются. Порядок `clan → user` согласован с оплатой кланового налога.
- Продажа блокирует актуального пользователя, затем выбранные строки рюкзака по ID. Сумма считается по текущему количеству, списание использует `WHERE count >= quantity`, начисление — SQL `increment`. Повторная полная продажа не приносит деньги; повторная частичная продаёт только фактический остаток, как и раньше при превышении запрошенного количества.
- Проверки владельца, надетого состояния и `is_sell` сохранены. Переполнение кошелька отклоняет всю продажу до списания. Ошибка лога откатывает также удалённый предмет. Старый Item с оставшейся записью в рюкзаке другого игрока не удаляется.
- Обычный и премиум-магазины читают существующие стаки через `lockForUpdate` с сортировкой по ID; добавление количества выполняется через `increment`, без сохранения устаревшего снимка `count`.
- Изменение управления корзиной, оставшиеся операции инвентаря и общие гонки членства клана в этот этап не входят. Миграции не требуются.

Проверки:

- Новые SQLite-регрессии: `TreasuryTransactionsTest` (8 сценариев) и `SellItemsTransactionsTest` (10 сценариев), включая реальные таблицы рюкзака и журналов.
- Связанные проверки магазинов, лимитов покупок, журналов, налога, банка и почты: **70 тестов, 331 проверка**, SQLite в памяти.
- `EconomyMysqlConcurrencyTest`: **10 тестов, 117 проверок** с двумя независимыми PHP-процессами и принудительным пересечением транзакций. Проверены двойные внесения, снятия разными участниками, встречные внесение/снятие, полные/частичные продажи, продажа одновременно с обычной/премиум-покупкой, покупка при удалении старого стака и независимое изменение количества под блокировкой рюкзака.

### Этап 2 — передача и выбрасывание: завершён (2026-11-02)

Закрыты критические пункты **4 и 5** (`ItemService::handOver/drop`).

- Передача блокирует обоих пользователей по возрастанию ID, затем строку рюкзака. Проверяются актуальные локации, владелец, надетое состояние и `is_give`. Переносится весь фактический стак с исходным экземпляром предмета, сроком действия и улучшениями; вместо удаления/создания строки меняется владелец. Повторная передача отсутствующего у отправителя предмета возвращает ошибку.
- Выбрасывание блокирует пользователя и строку рюкзака, проверяет `is_droppable`, надетое состояние и положительное количество. Изменение количества защищено SQL-условием `count >= quantity`; создание размещения и запись лога входят в ту же транзакцию. Квестовые предметы по-прежнему уничтожаются с уменьшением прогресса; ошибка откатывает действие.
- Частичный выброс создаёт отдельный Item: рюкзак и земля больше не делят один изменяемый экземпляр. Копируются атрибуты, камни/руны и назначение карты сокровищ. Старые экземпляры, уже разделяемые между рюкзаком и землёй/другим рюкзаком, также отделяются при переносе.
- Карта сокровищ сохраняет назначение при разделении/передаче, получает актуального владельца при подборе, а переносимый поиск отменяется. Подбор разных карт не объединяет их назначения в один стак.
- Подбор с земли блокирует актуального пользователя до размещения и использует его текущую локацию. Существующий стак читается под блокировкой; подобранный Item не удаляется, пока на него ссылаются другие записи рюкзака или земли. Деньги для ответа интерфейсу сохраняются без дополнительного запроса баланса.
- Выброшенный предмет не получает минутной резервации лута; шкатулка получает действие `pickup`. В данже размещение привязывается к сессии игрока.
- Передача и выбрасывание переведены на POST с CSRF. Обновлена форма выбора получателя; AJAX-выброс из рюкзака продолжает работать через существующий POST.

### Этап 3 — квесты: завершён (2026-11-03)

Закрыта гонка повторной сдачи личных/клановых квестов и переходов стадий из раздела «Высокое».

- Сдача вынесена из контроллера в `Application/UseCases/CompleteQuest`. Последний этап, расход требований, промежуточный предмет, финальные награды и статус сохраняются одной транзакцией. Раздельных коммитов последнего этапа и финального завершения больше нет.
- `QuestActionTransaction` задаёт блокировки для принятия, повторного запуска, отмены и сдачи. Личный квест: пользователь → персонаж → прогресс/рюкзак. Клановый: сначала клан и существующий прогресс, затем пользователи по ID (включая принявшего квест), персонаж и актуальное членство. Клановая отмена лидером согласована со сдачей принявшим игроком.
- В обе таблицы прогресса добавлен `revision`. Сдача требует ID записи прогресса и ожидаемую версию; устаревший запрос отвергается до расхода предметов/наград. Версия увеличивается при переходе, завершении и повторном запуске, поэтому старая форма не может сдать следующий этап или новый проход.
- Приём и сдача переведены с GET на POST с CSRF; маршруты квестов требуют авторизации. Обновлены кнопки NPC, страница квеста и последняя реплика диалога. GET-переходы между репликами остаются чтением.
- Клановый квест в процессе больше нельзя перезапустить другим участником. Параллельное принятие не дублирует выдаваемые предметы; повторный запуск после кулдауна сохраняет новую версию.
- `QuestInventoryService` суммирует одинаковые требования и списывает их из нескольких заблокированных ячеек. Нехватка суммарного количества отменяет действие; возвращаемый `false` старого `removeItemByShareItem` больше не игнорируется при сдаче.
- Награды вынесены в `QuestRewardService`, сохранены опыт, монеты, предметы, доступ к локациям, репутация и клановые очки. Денежная награда защищена от переполнения кошелька. Сообщения о принятии/завершении отправляются после коммита; внешняя отмена транзакции не оставляет уведомление о невыданной награде.

### Этап 4 — бой и данжи: завершён (2026-11-03)

Закрыты находки о конкурентном создании боя, уроне по одному спавну, побеге, финальной награде survival-данжа и очистке истёкшей сессии.

- Автоматическое нападение и ручная атака используют общий транзакционный вход. Перед входом повторно проверяются текущая локация, сессия данжа и доступность спавна. Пользователи блокируются по ID, создание сериализуется отдельной строкой `battle_entry_locks`, существующий бой читается под блокировкой. ### Этап 9 — ограничения балансов на уровне БД: завершён (2026-11-03)

## Уточнение после исправлений остатков — 2026-11-04

- **B-1 исправлен:** `applyChainAttack` блокирует запись второго участника, затем отдельно перечитывает `MonsterOnLocation` под `lockForUpdate`. HP/active проверяются на свежей строке; урон, сохранение HP и запись damage остаются внутри транзакции боевого хода. Выбор дополнительной цели упорядочен по ID. Блокировка `BattleDetail` сама по себе не блокирует eager-loaded spawn — поэтому eager load здесь заменён явным locking read.
- **R-1 исправлен:** удаление из рюкзака перечитывает ячейку под блокировкой с проверкой владельца, equipped и актуального количества, отвергает неположительное количество и возвращает false при отсутствии/нехватке. Повторный вызов со старой моделью не сообщает об успешном списании. Частичный decrement проверяет affected rows. Старый экземпляр Item сохраняется, если используется другой ячейкой рюкзака.
- **R-2 исправлен:** повторная выдача репутационного квеста увеличивает revision и сбрасывает runtime-таймеры стадии. Блокировка player сериализует выдачу одной пары player/quest, включая первоначальное создание.
- **R-3 исправлен:** unique-конфликт именно при INSERT `ClanLearnedSkill` перехватывается через `UniqueConstraintViolationException` внутри savepoint; наружу передаётся бизнес-ошибка `clan.action.skill_changed`. Тест инжектирует настоящий unique-конфликт через SQLite-триггер и проверяет полный откат.
- **R-4 исправлен:** создание `BattleDetail` использует locking `firstOrCreate` по battle + participant. Laravel обрабатывает unique-конфликт создания через savepoint; повторный вход переиспользует существующую строку.
