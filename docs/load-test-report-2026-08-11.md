# Отчёт нагрузочного тестирования — 2026-08-11

## Итог

Приложение выдержало 50 одновременно активных игровых HTTP-сессий без 5xx и без потерянных запросов, но приемлемая интерактивная производительность заканчивается раньше:

- до 5 активных игроков: общий p95 ниже 0,7 секунды;
- 10 активных игроков: общий p95 1,34 секунды;
- 20 активных игроков: общий p95 2,41 секунды;
- 50 активных игроков: общий p95 5,30 секунды, максимум 7,45 секунды.

Основное ограничение текущего контура — пять PHP-FPM workers. Под нагрузкой были одновременно насыщены PHP и MySQL, а Nginx оставался почти незагруженным. Это тест активно нажимающих игроков, а не общего числа авторизованных пользователей, которые просто держат игру открытой.

## Изоляция данных

Исходная схема `game` скопирована в `game_load_test` через `mysqldump --single-transaction`. Приложение переключено на копию файлом `docker-compose.load-test.yaml`.

Проверки копии до теста:

- 124 таблицы в каждой схеме;
- совпали точные количества пользователей, игроков, боёв, деталей, раундов и ударов;
- совпали контрольные суммы таблиц `battles`, `battle_rounds` и `battle_round_hits`.

После теста исходная схема сохранила прежние количества и контрольные суммы:

| Таблица исходной схемы | Строк | Контрольная сумма |
|---|---:|---:|
| `battles` | 460 | 3305209493 |
| `battle_rounds` | 2 034 | 407874664 |
| `battle_round_hits` | 2 158 | 72577046 |

Laravel после переключения вернул активную схему `game_load_test`. На момент завершения отчёта приложение оставлено подключённым к тестовой копии.

## Сценарий HTTP-нагрузки

Для каждого виртуального игрока создавались отдельные:

- пользователь и cookie-сессия;
- игрок с характеристиками соответствующего диапазона;
- реальные экземпляры мобов;
- последовательность `POST /login` → начало боя → HTTP-раунды атаки → `GET /heal/{id}`.

Игроки распределены между тремя картами:

- Канализация — Канализационная крыса 1 уровня;
- Шепчущий Лес — Лесная Рысь 6 уровня;
- Забытый Курган — Костяной Волк 19 уровня.

Статы тестовых игроков заданы подготовщиком, чтобы они стабильно завершали бой. Поэтому 100% winrate этого теста проверяет серверный путь, но не игровой баланс.

На каждой ступени каждый игрок провёл два боя. Порог аварийной остановки: более 5% HTTP-ошибок.

## Docker

Во время максимальной ступени наблюдались приблизительные пики:

| Контейнер | CPU | RAM |
|---|---:|---:|
| PHP-FPM | 190,8% | 61,6 МиБ |
| MySQL | 100,4% | 604 МиБ |
| Nginx | 2,2% | 13,9 МиБ |
| Redis | менее 5% во время игрового теста | 6,4 МиБ |

PHP-FPM доходил до шести PID: master и пять максимально разрешённых workers. Память не является текущим пределом. Redis почти не участвовал, потому что сессии и кеш приложения настроены на файлы.

Compose не задаёт CPU/RAM limits, поэтому это относительный тест локального Docker Desktop, а не паспортная мощность будущего production-сервера.

| InnoDB row lock time | 188 870 мс | 188 954 мс | +84 мс |
| Temporary disk tables | 0 | 0 | 0 |
| Slow queries | 5 | 5 | 0 |

Performance Schema после сброса digest зафиксировала 894 `START TRANSACTION` и 894 `COMMIT`. Суммарное время `COMMIT` — 5,533 секунды, среднее — 6,189 мс. Deadlock и таймаутов приложения не обнаружено.

PDO выполняет основную массу SQL через native prepared statements, поэтому Performance Schema агрегировала их как `statement/com/Execute`, без полезного текста конкретных запросов. Для точной оптимизации SQL нужен отдельный короткий прогон с Laravel DB listener/Telescope либо временным slow query log с порогом порядка 100–200 мс.

|---|---:|---:|
| `users` | 8 | 108 |
| `battles` | 460 | 634 |
| `battle_rounds` | 2 034 | 2 934 |
| `battle_round_hits` | 2 158 | 3 436 |

Конкретно основной fixture создал 172 боя, 890 технических записей раундов и 1 264 записи ударов. Это подтверждает, что для многолетней игры понадобится политика хранения/архивации боевых логов.

## Автоматические и браузерные проверки

`php artisan test`:

- 4 теста прошли;
- 9 тестов упали;
- все 9 падений относятся к тестам кузницы и вызваны устаревшими классами `App\Models\Share\ShareItem`, `App\Models\Share\ShareRecipe` и `App\Models\User`.

Feature-smoke главной страницы прошёл. Ошибки тестов кузницы существовали независимо от копирования БД и требуют обновления namespace в тестовом коде.

Полный сбор browser timing не завершён: Chrome заблокировал автоматизацию открытым интерфейсом другого расширения, а встроенный браузер в окружении недоступен. Попытка загрузки страницы всё же выявила отсутствующие frontend-ресурсы в Nginx:

- `/main/js/canvas.all.js`;
- `/index.html`;
- `/library/img/torg_banner.png`;
- несколько файлов `/info/pictures/image/*.gif`;
- несколько изображений `/images/data/artifacts/*.gif`.

В логах не было PHP fatal, upstream timeout, 502, 503 или 504. Отсутствующие ресурсы нужно исправить до измерения LCP/INP/CLS.

## Выводы и приоритеты

1. Текущий практический предел для активно сражающихся игроков — около 5–10 одновременных действий, если целевой p95 должен оставаться в пределах 1–1,5 секунды. Это не предел общего online.
2. Увеличить `pm.max_children` с 5 можно только вместе с повторным тестом MySQL: на 50 игроках MySQL уже доходил примерно до одного полного CPU core.
3. Сначала собрать тексты самых дорогих SQL-запросов. Основной признак — около 56 MySQL Questions на один HTTP-запрос и более 300 тысяч logical reads за прогон.
4. После SQL-профилирования проверить `pm.max_children=8` и `10` отдельными одинаковыми прогонами. Сравнивать p95 и throughput, а не только отсутствие ошибок.
5. Исправить отсутствующие статические ресурсы и повторить browser performance audit.
6. Для горизонтального масштабирования перенести sessions/cache с файлов на Redis и добавить отдельный queue worker.
7. Ввести retention/архивирование `battles`, `battle_rounds` и `battle_round_hits`, иначе многолетняя история станет постоянной нагрузкой на индексы и резервное копирование.
8. Следующий этап — 30–60-минутный soak-тест с постоянными 10 и 20 активными игроками, затем отдельный hotspot-тест нескольких игроков на одном монстре для проверки `lockForUpdate`.

## Воспроизведение

Проверить активную БД:

```bash
docker compose -f ../docker-compose.yaml -f docker-compose.load-test.yaml exec -T php-www \
  php -r 'require "vendor/autoload.php"; $app=require "bootstrap/app.php"; $app->make(Illuminate\Contracts\Console\Kernel::class)->bootstrap(); echo Illuminate\Support\Facades\DB::scalar("select database()"), PHP_EOL;'
```

Подготовить новый fixture только на тестовой схеме:

```bash
docker compose -f ../docker-compose.yaml -f docker-compose.load-test.yaml exec -T php-www \
  php scripts/load_test_prepare.php --users=50 --monsters-per-user=10
```

Запустить HTTP-тест с хоста:

```bash
php scripts/http_game_load_test.php \
  --confirm-database=game_load_test \
  --stages=1,5,10,20,50 \
  --iterations=2 \
  --timeout=30 \
  --stop-error-rate=5
```

Сырые результаты текущего запуска: `storage/app/load-test/http-load-20260811_114950.json` и `storage/app/live_progression_result.json`.
