# Инцидент: очистка игровой базы конкурентным тестом

## Установленная причина

Ошибка внесена агентом в `tests/Feature/Modules/Commerce/RewardTradeMysqlConcurrencyTest.php` на этапе 8 исправления race conditions. Очистка фикстур выполнялась так:

```php
foreach (Schema::getTableListing() as $table) {
    DB::table($table)->delete();
}
```

В установленном Laravel `Schema::getTableListing($schema = null, $schemaQualified = true)` без схемы перечисляет все доступные несистемные схемы и возвращает квалифицированные имена. `MySqlGrammar::compileSchemaWhereClause()` при `null` исключает только системные схемы. Поэтому проверка имени текущей тестовой базы не ограничила цели DELETE: `game.users` явно адресует другую базу даже из тестового подключения. Очистка выполнялась с отключёнными FK-проверками.

Это ошибка тестовой обвязки и проверки изоляции агентом. Утверждения в отчёте этапов 8–9, что тесты не затрагивали игровую базу, неверны. Последняя миграция CHECK не является причиной первоначальной потери строк: до неё `users` уже была пуста. Однако ссылаться на это как на доказательство безопасности предыдущих тестовых запусков было неправильно.

## Подтверждённые события

- Бэкап `game_2026-11-03_16-00-01.sql.gz` содержит INSERT для users, players, items, share_items, locations и migrations. Это 16:00 UTC / 18:00 по Киеву. В копии за 17:00 UTC этих INSERT уже нет.
- Сохранена исходная копия `binlog.000089`. Заголовки событий и Table_map/Delete_rows разобраны read-only. Межсхемная очистка начинается 2026-11-03 **16:06:52 UTC / 18:06:52 Киев** с тестовых/кандидатной баз. Первое найденное удаление в `game` — `artifact_upgrade_configs`, позиция **30763820**, **16:06:55 UTC**.
- В том же проходе удаляются `game.backpacks` (16:06:55 UTC), `items`, `clans`, `locations` (16:06:56), `migrations`, `players` (16:06:57), `share_items` (16:07:00), `users` (16:07:02; позиция **51136219**). Это DELETE строк, не DROP DATABASE.
- Delete_rows затрагивают также другие доступные схемы: codex_candidate, game_load_test, game_recovery, game_pre_recovery_backup_20260926, schema_reference и тестовые базы. Это не резервные источники, на которые можно теперь полагаться без проверки.
- Последующий повтор того же теста на этапе 9 также использовал ошибочную очистку. Успешные assertions проверяли только тестовую фикстуру и не обнаруживали удаление чужих данных.
- Перед миграцией кошельков и после неё количество users было 0. Миграция установила только два CHECK; чтение метаданных и дампы до/после подтвердили отсутствие изменения строк непосредственно этой миграцией.

Последний бэкап перед CHECK-миграцией уже содержит потерю данных и не подходит для восстановления исходного состояния.

## Сделано после обнаружения

- Опасный общий обход схем удалён. Очистка теперь имеет фиксированный список неквалифицированных имён таблиц фикстуры и закреплённое проверенное подключение.
- Выполнена только проверка синтаксиса исправленного PHP-файла (`php -l`); тестовые сценарии после обнаружения не запускались.
- База не восстанавливалась, настройки/права MySQL не менялись. Пользователь ранее потребовал не переносить восстановленные данные в основную базу без его подтверждения; это ограничение остаётся в силе.

## Дальнейшие действия

До новых интеграционных прогонов нужна изоляция прав тестового пользователя на единственную тестовую схему (либо отдельный сервер), а также проверка отсутствия побочных изменений в соседней контрольной схеме. Одной проверки `getDatabaseName()` недостаточно.

Восстановление сначала подготовить в отдельной базе из сохранённого полного бэкапа, проверить состав таблиц, старые ID, связи и изменения между бэкапом и началом удаления. Повторное проигрывание binlog должно исключать разрушительные транзакции; точная граница восстановления ещё не подготовлена. Основную базу заменять только после подтверждения пользователя.

## Восстановление по подтверждению пользователя

Пользователь явно указал: «востанавливай бекап за 18 00». Основная `game` восстановлена из `game_2026-11-03_16-00-01.sql.gz` (16:00 UTC / 18:00 Киев). Binlog после этой точки не применялся.

- До импорта повторно проверены SHA-256 источника (`b3b5ddff6c679540ccdcfbdb51c7699c26f4789d47c9a51d81950fe4b84fc13c`), целостность gzip и отсутствие USE/CREATE DATABASE/DROP DATABASE в дампе.
- Дамп сначала загружен в отдельную `game_restore_1800_20261103`. Проверены 231 таблица, 9 пользователей, 9 персонажей, 778 items, 179 backpacks, 1703 locations, 1296 share_items, 1 клан, 298 исходных записей migrations; некорректных кошельков нет.
- На время основного импорта остановлены nginx-www, phpmyadmin, php-www, reverb, queue-worker и scheduler. MySQL/Redis/Mailpit оставались запущены.
- Текущее повреждённое состояние предварительно сохранено в `storage/app/recovery/2026-11-03_trade_test_incident/game_before_restore_1800_1793738401268.sql.gz`, gzip проверен, права 0600, SHA-256 `0577c553e4b6976d8135ebaa405778d186738929aaad7f6db8c3effda0fd7b33`.
- Импорт в `game` выполнен непосредственно из проверенного исходного gzip, без DROP DATABASE и без `--force`; ошибок SQL не было. До возобновления работы сервисов SHA-256 полного упорядоченного дампа всех строк основной и проверочной баз совпали: `53684f69ff1d991589e0795cc18067566c149e4cff388595cc618c598ec2b4f0`. Это проверка полного содержимого, а не только количества строк; исходные ID сохранены.
- После совпадения данных отдельно повторно применена только ранее согласованная миграция `2026_11_03_000004_add_wallet_balance_constraints.php`. Оба CHECK включены (`ENFORCED=YES`); все остальные миграции/сидеры не запускались. Эта миграция добавляет запись в migrations и ограничения, не изменяет игровые строки.
- Повторно проверены количества основных сущностей. Нет users с отсутствующим player, players с отсутствующим user, backpacks с отсутствующим item или user (все четыре проверки — 0).
- Все остановленные сервисы запущены обратно. Главная `/` и `/register` отвечают HTTP 200. GET `/login` отвечает 405, поскольку вход выполняется POST; авторизационные данные игроков не менялись и попытки входа за них не выполнялись.
- Автоматические/конкурентные тесты не запускались. Соседние повреждённые базы не восстанавливались; проверочная база и исходный gzip сохранены.
