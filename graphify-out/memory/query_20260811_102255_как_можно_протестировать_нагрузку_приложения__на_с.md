# Q: как можно протестировать нагрузку приложения, на сервер? на браузер пользователя на базу данных?

## Answer

Expanded from original query via vocab: [request, controller, battle, fight, attack, player, user, users, session, database, query, cache]. Recommended three-layer plan: k6 protocol load for authenticated location/fight/item journeys, a small concurrent k6-browser/Chromium layer for Core Web Vitals, and MySQL Performance Schema plus temporary slow-query logging during application-driven load. The highest-risk route is GET /fight/attack/{id}/{monsterId}/{action}: FightOrchestrator wraps every round in a DB transaction, locks battle_details, updates battle/player/user/monster/round data and writes hit rows. Current Docker PHP-FPM pm.max_children is 5, so only five simultaneous PHP requests are served. Session/cache are files and queue uses MySQL. Load tests must use representative historical battle data because one live 1-26 run already creates 636 battles and 6136 combat rounds; no battle-history pruning was found.
